# 후원배치 규정 (Placement Rules)

> 포르투나 보상 시스템의 **후원(placement) 배치·카운팅 규정** 단일 소스.
> 최종 확정: 2026-07-12 (사용자 이미지 기준). 이 문서와 엔진(`supabase/migrations`)이 어긋나면 이 문서를 정본으로 본다.

---

## 1. 두 개의 끈 (Two Strings)

회원은 서로 독립적인 두 상위 링크를 가진다.

| 끈 | 컬럼 | 용도 | 제약 |
|---|---|---|---|
| **추천 (Referral)** | `recommender_id` | 수당 귀속 (레벨 수당의 세대 체인) | **마케터만** 가능 (트리거 `assert_recommender_is_marketer`) |
| **후원 (Placement)** | `parent_id` | 조직도 위치 (직급·공유 수당의 계보) | 역할 제한 없음 (구독회원도 하위 보유 가능) |

- 두 값이 다를 수 있으며, 다른 경우를 **스필오버(spillover)** 라 한다.
- 후원 트리는 클로저 테이블 `placement_closure(ancestor_id, descendant_id, depth)` 로 관리한다 (회원 INSERT 시 트리거 자동 유지).

---

## 2. 배치 규정 (핵심)

### 규정 2.1 — 첫라인 = 주력 라인
마케터의 **첫라인(주력 라인)은 시스템적으로 무조건 대실적 라인**이다. 좌측 한 라인으로 표현한다.

### 규정 2.2 — 직접추천자를 첫라인 하부에 몰아준다 (밀어주기)
마케터가 여러 명을 직접추천하면, 아무 데나 분산 배치하지 않고 **직접추천한 사람을 자기 첫라인(주력)의 하부에 후원(`parent_id`)으로 계속 몰아넣는다.** 분산하면 대실적이 쌓이지 않는다.

> **예시 (이미지):** A가 B·C·D·G·J 를 직접추천 → **G·J 를 자기 첫라인 B 의 하부에 후원으로 배치.**
> 첫라인이 하나의 깊은 수직 계보로 누적된다: `B → E → F → G → H → I → J`

### 규정 2.3 — 배치 위치 = 주력 라인 최하단
스필오버 배치 시 대상자는 **대실적 라인의 가장 깊은 노드(최하단) 밑**에 매단다.
구현: `lowest_node_of_major_leg(m)` → `move_placement_subtree(node, newParent)`. 동률은 depth → id 순.

## 2-B. 자리(slot) 규정 — 2026-09-05 확정 (엔진 0037 반영)

| 항목 | 규정 |
|---|---|
| 자리 번호 | 회원은 후원 부모 아래 자리 번호(`placement_slot`)를 가진다. **1번 = 주력 라인(좌측) 머리.** |
| 1번 자리 | **파트너 전용.** 추천인의 직추 중 **처음 파트너가 되는 사람**이 파트너 전환 시점에 시스템이 1번에 고정(잠금). 구독회원은 1번에 들어갈 수 없다. |
| 이미 배치된 뒤 파트너 전환 | 2번 이후에 배치된 구독회원이 나중에 파트너가 돼도 자리는 그대로. 1번은 다음 "미배치 첫 파트너"를 기다린다. |
| 배치 대기 | 구독을 시작한 직추는 추천인의 "배치 대기"에 오른다(등록회원은 트리 밖). |
| 수동 배치 | 추천인(파트너)이 **자기 후원 조직 안** 원하는 노드 아래에 배치. 자리는 그 노드의 다음 빈 번호(2번 이상). 화면은 "1번 라인 최하단"을 권장으로 먼저 제시. |
| **한 번만** | **후원배치는 딱 한 번.** 확정(`placement_locked`) 후 파트너 본인은 변경 불가. 관리자만 사유를 남기고 이동(`placed_by='admin'`, `placement_note`). |
| 방치 | 첫 구독 결제 후 **7일** 지나도 미배치면 시스템이 **1번 라인 최하단**(1번 라인이 없으면 추천인 바로 아래)에 자동 배치·확정. 일일 크론(`/api/cron/renewals`)에서 `auto_place_pending(7)`. |
| 주력 라인 판정 | `get_major_minor`·`lowest_node_of_major_leg` 는 **1번 자리 라인**을 주력으로 본다(1번이 없으면 종전대로 활성 최다 라인). |

구현: `place_member(member, new_parent, by, note, slot)` 단일 진입점 · `place_first_partner` (upgrade_to_marketer 내부) · 파트너 화면 `내 팀 → 후원배치 대기` · 관리자 `회원 상세 → 후원배치 이동`.

## 3. 후원계보 상위 누적 (Roll-up)

### 규정 3.1 — 상위는 하위 전원을 자기 계보로 카운트한다
후원계보에서 **위쪽 사람은 자기 아래에 매달린 전원을 자기 후원 산하(downline)로 카운트**한다.

> **예시:** 최하단 **J 가 300명**을 만들어 직급이 되면, J 위쪽의 **I·H·G·F·E·B 전원**도 그 300명을 자기 후원계보로 포함한다 → 각각 301·302·303·304·305·306명이 되어 **함께 직급이 오른다.**
>
> → J 위쪽 마케터 입장에서는 **본인이 알지도 못하는 하위(J) 덕분에 실적이 붙는 스노우볼**이 된다.

### 규정 3.2 — 대실적은 그 라인 전체가 누적된다
한 라인이 깊게 뻗으면 그 라인에 쌓인 인원 전체가 상위의 대실적이 된다.

> **예시:** J 가 5000명이 되고, H 가 2번째 라인에 4000명을 만들면 →
> H 위의 **G·F·E·B·A** 는 (라인이 하나뿐이므로) 그 한 라인에 쌓인 **9000명 전체를 대실적**으로 가진다.

## 4. 대실적 / 소실적 정의

각 마케터의 직속 자식(=`parent_id`가 그 마케터인 노드) 하나하나가 하나의 **라인(leg)**이며, 라인 실적 = 그 라인 서브트리(클로저) 안의 **활성 구독자(`is_active_subscriber`) 수**.

- **대실적 (Major)** = `MAX(라인별 활성수)` — 가장 큰 한 라인
- **소실적 (Minor)** = `SUM(전체) − MAX` — 나머지 라인 전부의 합
- **총 활성** = `SUM(전체)`
- **바이너리(2진) 아님** — 라인 수 제한 없음.

---

## 5. 카운팅과 직급·수당 연결

- **직급 산정 기준** = 후원 산하 **전체 활성 구독유저수**(`total_active`). 1~3직급은 직접추천 활성수(`min_direct`)로도 인정.
- **직급 = 순수 카운트** — 30% 무관, 강등 없음. (예: 5직급 조건 충족 시 5직급 직급수당 100% 지급)
- **30% 균형 게이트는 '공유수당'에만** — 5직급+ 는 `소실적 / 전체 ≥ 30%` 일 때만 공유수당 수령. 3·4직급은 무조건.
- 상세 요율·계산식은 `docs`(추후) 또는 `settlement-engine` 참조. 배치 규정 범위 밖.

## 6. 조직도 시각화 규칙

`components/trees/member-tree.tsx` 기준.

- **주력 라인 = 좌측 spine, 녹색 강조, `maxDepth`까지 깊게** 펼침 + 머리에 "주력 라인" 라벨.
- **소실적 라인 = 얕게** (노드 + `+N 하위` 칩).
- 스필오버 노드(추천인 ≠ 후원부모) = 앰버 `· 스필오버` 표시.
- spine 정렬: 활성 → activeCount 내림차순 (좌측 i=0 = 주력 라인).

## 8. 미확정 항목 (사용자 확정 필요)

1. **자동 배치 훅** — 규정 2.2 의 "직접추천자를 첫라인 최하단에 후원 자동 배치"를 등록/추천 플로우에 자동 훅으로 걸 것인가? (현재 수동)
2. **직급 임계값** — 이미지는 `300명 = 1직급` 이나, 현행 `ranks` 는 `300 = 2직급`(1직급 = 직추 2명). 임계값을 이미지 기준으로 바꿀지, 예시 숫자로 볼지.
3. **공(空)코드 처리** — 마케터가 첫라인에 유저를 등록만 하고 구독 미결제 → 한 달 뒤 결제·연회비 납부 시 배치/실적 소급 규칙.
4. **압축 롤업·회복** — 중간자 비활성 시 볼륨 압축 전달은 구현됨. 그 중간자가 재활성화될 때 회복 규칙.
5. **혼합 카운팅 확정** — 대실적 라인 + 소실적 라인이 큰 규모로 공존할 때(예: 대실적 1000 + 소실적 2000) 직급·30% 게이트 적용 재확인.
